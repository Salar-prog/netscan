# PM Review — NetScan as Self-Deployable Product

**Reviewer perspective:** Product Manager at a mid-size company wanting to ship this as a self-deployable IPAM/discovery tool that customers install on-prem.

**Date:** 2026-08-27
**Current state:** v0.1.0 + production polish (133 tests, CI green, Postgres tested)

---

## 1. Can We Ship Today?

### What's Good (ship-ready)
- Core product promise holds: safe quarantine model, multi-probe scanner, no false frees
- API is well-structured with RBAC, rate limiting, idempotency keys, structured errors
- Dashboard is functional with server-rendered HTMX (no Node build step)
- Docker image builds and passes healthcheck
- CI runs lint + test (SQLite + Postgres) + Docker on every push
- Auth is solid: API keys + optional LDAP/AD, session cookies, RBAC enforcement
- Security hardening is comprehensive: SSRF blocklist, webhook HMAC signing, correlation IDs
- Deployment docs (README, .env.example) cover the basics

### What Blocks a Self-Deployable Launch

**BLOCKER: Documentation is stale and incomplete for a customer-facing product.**

A customer cloning this repo and reading the README will:
1. Not know about key lifecycle features (PATCH endpoint, soft revoke, key expiry)
2. Not know about the /metrics endpoint or retention policy
3. Not see the Postgres CI badge (only SQLite badge shown)
4. Miss the scheduler health check in /health
5. Not understand the full configuration surface (DISABLE_BOOTSTRAP, RETENTION_DAYS)
6. Get a broken deploy if they follow the API doc's reserve example (wrong payload format)

**BLOCKER: API reference (docs/api.md) is missing critical endpoints.**
- PATCH /auth/keys/{id} not documented
- /metrics endpoint not documented
- Scheduler health check not documented
- Reserve example has wrong payload format

**BLOCKER: Production readiness doc (docs/PRODUCTION_READINESS.md) is misleading.**
- Lists many findings as [REPRODUCED] that are now fixed
- Section 6 backlog items B1-B9 are completed but not reflected
- A PM reading this would think the product isn't ready — but it is

## 2. What's the Real Launch Blocker?

Not the code — the code is solid. The blocker is **trust at first impression.**

A customer evaluating this will:
1. Read the README → see missing features, outdated config table
2. Read the API doc → try the reserve example → get a 422 → think the API is broken
3. Read PRODUCTION_READINESS.md → see [REPRODUCED] findings → think it's not ready
4. Try to find the PATCH endpoint for key management → can't find it in docs → think it doesn't exist

The product works. The docs don't tell that story.

## 5. Competitive Positioning

**What NetScan does that alternatives don't:**
1. Safe quarantine model (no false frees) — unique differentiator
2. Multi-probe scanner (ARP + ICMP + TCP SYN) with capability detection
3. Zero external dependencies (no Redis, no Celery, no Postgres required)
4. Server-rendered dashboard (no Node.js build step)
5. API-first with RBAC, rate limiting, idempotency
6. HMAC-signed webhooks with retry/backoff

**What NetScan lacks vs. competitors (e.g., NetBox, PHPIPAM):**
1. No IPv6 support
2. No CSV/JSON export
3. No HA story (single-instance constraint)
4. No TLS termination (relies on reverse proxy)
5. No OIDC/SAML (LDAP only)

**Recommendation:** Position as "lightweight IP discovery for homelab/SMB" — not a full IPAM replacement. The safe quarantine model is the killer feature. Lead with that.
